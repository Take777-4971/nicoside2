# NicoSide (pywebview版)

## 今回の修正内容

### 1. ピン留めボタンでアプリが固まる問題

`window.on_top` の変更を、JS側からのAPI呼び出しと**同じスレッド上で直接**
行っていたことが原因です。特にWindowsのEdgeChromiumバックエンドでは、
js_apiの呼び出しがUIスレッド上で処理されることがあり、そこから
ウィンドウのプロパティ変更（内部的にUIスレッドへの処理依頼を行う）を
呼ぶと、自分自身を待ち続ける形になりフリーズします。

`api.py`の`toggle_on_top()`を、**別スレッドで`window.on_top`を変更する**
形に修正しました。

```python
def toggle_on_top(self):
    window = webview.windows[0]
    new_state = not window.on_top
    done = threading.Event()

    def _apply():
        try:
            window.on_top = new_state
        finally:
            done.set()

    threading.Thread(target=_apply, daemon=True).start()
    done.wait(timeout=2)
    return new_state
```

このLinux環境（GTKバックエンド）では、2回連続でピン留めボタンを押しても
フリーズせず正常にトグルできることを確認しています。ただし、Windowsの
EdgeChromium特有の挙動はこの環境では再現できないため、**実機での確認を
お願いします**。まだ固まる場合はお知らせください。

### 2. 動画が再生できない問題

HTMLをローカルの`file://`から直接読み込んでいたことが原因の可能性が
高いです。YouTubeの埋め込みプレーヤーは、`file://`（オリジン無し）から
開かれた場合に「動画を再生できません」となることが知られています。

`webview.start(http_server=True)` を指定し、pywebview内蔵のHTTPサーバー
（`http://127.0.0.1:port/`）経由でHTMLを配信するように変更しました。
このLinux環境で`location.protocol`を確認したところ、`file:`から`http:`
に変わったことを確認しています。

### 3. 検索結果が実際のキーワードと一致しない問題

`search()`が固定のダミーデータを返す実装のままだったのが原因でした。
実際の検索APIに接続する実装に差し替えました。

- **ニコニコ動画**: 公式の[スナップショット検索API v2](https://site.nicovideo.jp/search-api-docs/snapshot)
  に接続。APIキー不要、無料で利用できます（非営利目的の解析用途限定）。
- **YouTube**: [YouTube Data API v3](https://developers.google.com/youtube/v3/docs/search/list)
  に接続。**APIキーの取得が必要**です（後述）。

レスポンスの解析ロジックは、両APIの公式ドキュメントに記載されている
サンプルレスポンスを使って単体テスト済みです（実際のネットワーク通信は
このサンドボックス環境では実行できないため、実機での最終確認をお願い
します）。

#### 検索結果のページング

5件ずつ表示し、下部に「先頭に戻る／前へ／次へ／末尾に進む」ボタンを
追加しました。

- **ニコニコ動画**: オフセット方式のAPIのため、先頭・前へ・次へ・末尾
  すべて対応しています（総件数も表示されます）。
- **YouTube**: `nextPageToken`方式のAPIのため、**前へ・次へ・先頭に戻る**
  のみ対応しています。「末尾に進む」ボタンはYouTube選択時は非表示に
  なります（API側の制約で任意ページへのジャンプができないため）。

#### YouTube APIキーの設定方法

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作成
2. 「APIとサービス」→「ライブラリ」から **YouTube Data API v3** を有効化
3. 「認証情報」から APIキーを発行
4. 以下いずれかの方法でアプリに設定
   - 環境変数 `YOUTUBE_API_KEY` を設定する
   - `config.json.example` を `config.json` にコピーし、
     `"youtube_api_key"` に発行したキーを設定する

APIキーが未設定の場合、検索結果に「YouTube Data APIキーが未設定です」
という案内が表示されます（アプリが落ちることはありません）。

**注意**: YouTube Data APIには1日あたりの無料利用枠（クォータ）があり、
検索1回につき比較的多くのクォータを消費します。使いすぎるとその日は
検索できなくなる場合があります。

### 4. 鍵ボタンを押すと常にYouTubeが選択される件（未修正・今後の課題）

現状、鍵ボタンは「YouTubeにログイン」専用のボタンとして実装しているため、
押すとソースの選択が強制的にYouTubeに切り替わります。ニコニコ動画選択中
に押しても同様です。ご要望通り「将来的な課題」として残しています。対応
する場合は、たとえば

- ソースごとにログインボタンを分ける
- 現在選択中のソースがログイン非対応な場合はボタン自体を無効化する

といった方向性が考えられます。

## 追加対応（今回の更新分）

### ピン留めのON/OFFが見た目でわからない
`color`をemoji（📌）に適用しても、多くの環境でemoji自体の色は変わらない
ため、実質的に見た目が変化していませんでした。ボタン全体の**背景色**を
ON時はアンバー色、OFF時は透明にし、さらに「ON」「OFF」のテキストラベル
も併記するようにしました。

### 検索結果の表示件数をウィンドウサイズに応じて自動調整
結果一覧エリアの高さを取得し、1件あたりの目安の高さ(約63px)で割って
表示件数を自動計算するようにしました。ウィンドウをリサイズした場合も
（デバウンス付きの`resize`イベントで）自動的に再計算し、現在の検索を
1ページ目から取得し直します。「前へ／次へ」（および先頭・末尾）の
ページングUIはそのまま最下部に残しています。

### 初期選択ソースをYouTubeに変更
`Api`内のプロバイダ辞書の順序を変更し、起動時にYouTubeが選択された
状態になるようにしました。

### ウィンドウサイズの切り替えボタン
ヘッダーに⛶ボタンを追加し、クリックするたびに
**最小(1倍・340×680) → 2倍(680×1360) → 3倍(1020×2040) → 最小 …**
と切り替わるようにしました。倍率に応じてボタンの色も変化します
（緑=2倍、青=3倍）。

## 拡大方法の見直し（今回の更新分）

「拡大」ボタンの挙動を、単にウィンドウ全体を大きくするだけのものから、
以下のように改善しました。

### 拡大方向をウィンドウの画面上の位置で決める
- アプリの左上座標がディスプレイの**左寄り**にある場合: 左上を固定して
  右下方向へ拡大
- アプリの左上座標がディスプレイの**右寄り**にある場合: 右上を固定して
  左下方向へ拡大

`webview.screens`でディスプレイ情報を取得し、ウィンドウの中心座標が
画面の中心より左か右かで判定しています。

### 下端はディスプレイをはみ出さない
縦方向は常に上端固定・下方向への拡大ですが、ディスプレイの下端を
超える分は伸ばさないようにしました。ウィンドウが画面からはみ出すこと
よりも、画面に収まる範囲で最大限拡大することを優先しています。

### 拡大の目的はプレイヤー領域を広げること
これまでは結果一覧の表示件数だけが増える形でしたが、ウィンドウの
高さが基準サイズ(680px)を超えた分は**そのまま動画プレイヤーの高さに
上乗せ**するようにしました。結果一覧の表示件数は基準サイズの時と
ほぼ変わらず、拡大した分の大半が動画再生エリアの拡大に使われます。

### 動作確認
このLinux環境ではX11のウィンドウマネージャ（openbox）を導入し、実際に
右寄りに配置したウィンドウを拡大した際、右端の座標が保持されること
（左方向へ正しく拡大されること）を確認しました。Windows実機では
Win32 APIで座標を直接計算する実装のため、同様に動作するはずです。

## サイズ変更・検索結果・リピート再生（今回の更新分）

### サイズ選択をボタンクリックのサイクルからリスト選択に変更
⛶ボタンをクリックすると x1/x2/x3 の選択肢がポップアップで表示され、
選びたいサイズを直接クリックして切り替えられるようにしました。

### 手動でウィンドウをリサイズしても動画エリアが大きくならないように修正
これまでは、ウィンドウの高さが変わるたびに（サイズ選択ボタンでも手動
ドラッグでも）動画プレイヤーの高さが自動的に再計算されていました。
このため、x1のまま手動でウィンドウを縦に伸ばすと、意図せず動画エリア
まで大きくなってしまう問題がありました。

修正後は、動画プレイヤーの高さは**x1/x2/x3のサイズ選択をしたときだけ**
更新されます。手動でウィンドウをドラッグしてリサイズした場合は、動画
プレイヤーの高さはそのまま変わらず、増えた分の余白は検索結果一覧の
表示件数の増加にあてられます。

### 検索結果は最大100件まで
これまでは総ヒット件数が多いキーワードだと、ページ送りで際限なく
（ニコニコ動画なら数万件、YouTubeなら理論上さらに多く）閲覧できる
状態でした。実用上見る可能性があるのはせいぜい100件程度という想定で、
**保持・閲覧できる検索結果を最大100件までに制限**しました。
100件に達すると「次へ」「末尾へ」のボタンがそこで止まります。

### リピート再生
🔁ボタンで、再生中の動画をリピート再生できるようにしました。

- **YouTube**: 公式のURLパラメータ（`loop=1`と`playlist=<同じ動画ID>`の
  組み合わせ）で対応。単体動画のループはこの組み合わせでないと機能しない
  というYouTube側の仕様上の制約です。
- **ニコニコ動画**: 埋め込みプレーヤーにループ再生用の公式URLパラメータが
  提供されていないため、**現時点では非対応**です（ボタンを押しても
  ニコニコ動画の再生には反映されません）。postMessageベースの非公式な
  制御手段は存在するようですが、ドキュメント化されておらず信頼性が
  低いため、今回は見送りました。

## 再生リスト・初期表示サイズ（今回の更新分）

### YouTube再生リストの表示（ソースごとに処理を分離）
ソース選択（YouTube / ニコニコ動画）で、リスト関連のUI・処理を丸ごと
切り替える方針にしました。現時点では**YouTubeの再生リストのみ**対応
しています。

- ここでの「リスト」は既存のYouTube再生リストを指し、**このアプリから
  の編集はできません**（一覧から選んで表示するだけの読み取り専用）。
- ソースをYouTubeにすると「再生リスト:」の選択欄が表示され、選ぶと
  その再生リストの動画が検索結果と同じ一覧UI（ページングも含む）に
  表示されます。
- ソースをニコニコ動画に切り替えると、この選択欄ごと非表示になります。

**設定が必要です**: 本来「自分の再生リスト一覧」を取得するにはGoogle
アカウントでのログイン(OAuth)が必要ですが、今回はAPIキーのみで完結する
範囲に収めるため、**指定したチャンネルIDの「公開されている」再生リスト
一覧**を取得する方式にしました。`config.json`（または環境変数
`YOUTUBE_CHANNEL_ID`）にチャンネルIDを設定してください。

```json
{
  "youtube_api_key": "...",
  "youtube_channel_id": "UCxxxxxxxxxxxxxxxxxxxxxx"
}
```

非公開・限定公開の再生リストは（OAuthログインをしていないため）一覧に
出てきません。もし「自分専用の非公開リストも見たい」という場合は、
OAuthログインの実装が別途必要になります。

### 初期表示サイズをガジェットらしい形に変更
起動直後（x1）から、x2・x3のときと同じ考え方でディスプレイの端に
収まるサイズになるようにしました。

- ウィンドウの高さ = ディスプレイの高さいっぱい
- ウィンドウのy座標 = 0（ディスプレイ最上部）
- 幅だけが x1/x2/x3 の倍率で変わる

起動後、`window.events.shown`イベントで自動的に`select_window_size(1)`
相当の処理が走り、この状態に調整されます。

### 動画プレイヤーの高さの決め方を変更
これまでは「ウィンドウの高さ」を基準にプレイヤーの高さを決めていました
が、初期表示サイズの変更により、ウィンドウの高さは常にディスプレイの
高さいっぱいで一定になったため、この基準が意味をなさなくなりました。

代わりに、**プレイヤー領域の実際の描画幅から16:9になるように高さを
自動計算**する方式に変更しました。x1/x2/x3でウィンドウの「幅」が変わる
ことで、プレイヤーも幅・高さともに自然に拡大・縮小します。逆に、手動で
ウィンドウの高さだけをドラッグして変えても（幅が変わらない限り）
プレイヤーの大きさは変わらず、増えた余白は検索結果一覧の表示件数に
反映されます。

### 動作確認
このLinux環境で実際にウィンドウを起動し、以下を確認しました。

- 起動直後、ウィンドウが `y=0・高さ=ディスプレイの高さいっぱい・
  幅=基準サイズ` の状態になること
- YouTube選択時に再生リスト欄が表示され、選択すると一覧にその再生リスト
  の動画が反映されること。ニコニコ動画に切り替えると欄ごと非表示になる
  こと
- プレイヤーのアスペクト比が x1・x2 のどちらでも約16:9(1.78)に保たれる
  こと。x2選択で幅・高さとも拡大されること
- ウィンドウの高さだけを手動でリサイズしても、プレイヤーの高さは
  変わらないこと（実際に高さを300px縮めて確認）

なお実装の過程で、`window.events.shown`のコールバックが辞書を返す
とpywebview内部でエラーになり初期リサイズが適用されない不具合を検出し、
修正しました（戻り値を返さないラッパー関数に変更）。

## ウィンドウ端スナップ・OAuthログイン・リストリピート（今回の更新分）

### ① ウィンドウを画面端にドラッグすると吸着する
`window.events.moved`でドラッグ中の座標を受け取り、画面の左右端から
40px以内に近づいたら、ウィンドウの端をピッタリ画面端に合わせるように
しました（`api.py`の`handle_window_moved`）。モックしたウィンドウ・画面
でのユニットテストで、左端・右端それぞれへの吸着、および閾値外では
何もしないことを確認済みです。実際のドラッグ操作そのものはこの環境では
再現できないため、実機での使用感を確認してください。

### ② APIキーを廃止し、OAuthログインに変更
一般公開を見据え、APIキーをアプリに同梱する方式をやめました。代わりに
Googleの「インストールアプリ向けOAuth 2.0」フローに対応しました
（`auth.py`）。

- ログインは埋め込みWebViewではなく、**必ずシステムの既定ブラウザ**で
  行われます（`google-auth-oauthlib`の`InstalledAppFlow.run_local_server()`
  を使用。ローカルに一時的なHTTPサーバーを立て、ブラウザでのログイン後
  リダイレクトでトークンを受け取る、Google公式のデスクトップアプリ向け
  推奨パターンです）。
- 取得したトークンは`token.json`にローカル保存され、次回起動時は
  リフレッシュトークンで自動更新されるため再ログイン不要です。
- ヘッダーの👤ボタンでログイン状態を確認・ログイン／ログアウトの
  切り替えができます（ログイン済みは緑色表示）。

**開発者側の準備が必要です**: OAuthクライアント自体（`client_secret.json`）
は、各自でGoogle Cloud Consoleから取得して配置する前提です。詳しくは
下記「YouTube OAuthログインのセットアップ」を参照してください。

### ③ 再生リストをOAuthログイン後に取得
再生リスト一覧の取得を、これまでの「指定チャンネルIDの公開リストのみ」
から、**ログイン中のアカウント自身の再生リスト**（`playlists.list`に
`mine=true`を指定）に変更しました。これにより、非公開・限定公開の
再生リストも一覧に表示されるようになります（`channel_id`の設定は
不要になったため、関連コードごと削除しました）。

### ④ リストリピート（表示中のリスト・検索結果をリピート再生）
これまでの「1曲リピート」はそのまま残し、新たに「表示中の一覧（検索
結果または再生リストの、現在表示されているページ）を順番に再生し、
最後まで行ったら先頭に戻ってリピートする」機能を追加しました。

- 🔁ボタンをクリックすると、「リピートしない / 🔂1曲リピート /
  🔁リストリピート」を選ぶポップアップメニューが表示されます。
- **1曲リピート**は従来通り、YouTubeの埋め込みURLパラメータ
  （`loop=1&playlist=<同じ動画ID>`）で実現しています。
- **リストリピート**は、YouTubeの[IFrame Player API](https://developers.google.com/youtube/iframe_api_reference)
  を使って動画の再生終了を検知し、一覧内の次の動画へ自動的に進める
  方式です。通常のURL埋め込みだけでは実現できないため、リストリピート
  選択時のみ、通常の`<iframe>`ではなくこのAPI経由の再生に切り替わります。
- リピート対象は**現在一覧に表示されているページの動画のみ**です
  （ページ送りすると対象が変わります）。複数ページ・最大100件全体を
  シームレスに連続再生する機能は、以前ご相談した「連続再生機能の拡張」
  の範囲になるため、今回は含めていません。
- ニコニコ動画は対象外です（1曲リピートと同様、公式のAPIが提供されて
  いないため）。

**動作確認について**: このサンドボックス環境はYouTube公式のIFrame
Player APIスクリプト（`https://www.youtube.com/iframe_api`）を読み込め
ないネットワーク制限があるため、実際のYouTube動画では検証できません。
そのため、`YT.Player`をモックしたスタブに差し替えて、「動画終了イベントを
受け取ったら一覧の次の動画IDに切り替わり、最後まで行ったら先頭に戻る」
というロジック自体は正しく動作することを確認しました
（`v0→v1→v2→v0`と一巡することを確認済み）。実際のYouTube動画での
終了検知・自動再生については実機での確認をお願いします。

### YouTube OAuthログインのセットアップ

1. [Google Cloud Console](https://console.cloud.google.com/) でプロジェクトを作成
2. 「APIとサービス」→「ライブラリ」から **YouTube Data API v3** を有効化
3. 「APIとサービス」→「OAuth同意画面」を設定
   - 個人利用やテスト目的であれば「テストユーザー」に自分のGoogle
     アカウントを追加するだけで動作します
   - 不特定多数に配布する場合は、Googleによる審査（アプリ確認）が
     必要になる場合があります
4. 「認証情報」→「認証情報を作成」→「OAuthクライアントID」
   - アプリケーションの種類は **「デスクトップアプリ」** を選択
5. 作成後にダウンロードできるJSONファイルを `client_secret.json` という
   ファイル名でこのプロジェクトのルート（`main.py`と同じ階層）に配置

```
nicoside_pyweb/
```

## ピン留めUIの簡素化・自動的に隠すモード（今回の更新分）

### 右クリックでの最前面切り替えを廃止
背景の右クリックで最前面表示を切り替える機能は削除しました。ピンボタン
（📌）だけで操作する、よりシンプルなUIにしています。

### ピンボタンを3状態に変更
ピンボタンをクリックすると、ポップアップメニューで以下の3つから選べます。

- **OFF**: 最前面表示なし
- **常に最前面**: これまで通りの常時最前面表示（黄色）
- **自動的に隠す**: 常に最前面表示 ＋ 一定時間操作がないと画面端に
  自動的に畳まれる（赤橙色）

### 自動的に隠すモードの動作
「自動的に隠す」を選ぶと、以下のように動作します。

1. マウスカーソルがウィンドウから離れて5秒経過すると、ウィンドウが
   ドッキングしている側（左右どちらの画面端に寄っているか）に向かって
   幅がなめらかに縮み、最終的に10px程度の細いバー状になります
   （`api.py`の`_animate_resize`で、resize/moveをイーズアウトの
   カーブに沿って14ステップに分けて繰り返すことで、単純な瞬間切り替え
   ではない「にゅるっと」した動きを作っています）。
2. その細いバーにマウスカーソルが触れる（＝ウィンドウにカーソルが
   入る）と、同様になめらかに元のサイズへ戻ります。
3. 元のサイズに戻ったあと、再びマウスがウィンドウから離れれば、また
   5秒後に畳まれます。

ウィンドウの中身（検索バーやボタンなど）は畳まれても内部的にはそのまま
残っており、見た目上ウィンドウそのものが細くなることで「隠れる」ように
見える仕組みです。DOM側で表示・非表示を切り替える必要はありません。

### 実装中に見つけた不具合
`min_size=(300, 480)`を指定していたため、pywebviewが300px未満への
リサイズを拒否してしまい、畳んでも実際には300pxまでしか縮まらない
（意図した10pxまで縮まらない）不具合をテストで検出しました。
`min_size`を`(COLLAPSED_WIDTH, 200)`に変更し、正しく10pxまで畳まれる
ことを確認しています。

### 動作確認
モックしたウィンドウ・画面でのユニットテストで、左右どちらの端でも
アンカー位置を保ったまま正しい幅（10px⇔元の幅）まで変化すること、
モードを「自動的に隠す」以外に切り替えると自動的に元のサイズへ戻る
ことを確認しました。また実際にウィンドウを起動し、ピンメニューの
開閉・モード選択・マウスの出入りをシミュレートした一連の操作で、
畳む→展開が正しい幅で行われることも確認しています。

ただし、実際のマウスドラッグ操作や「にゅるっと感」の見た目・タイミング
（アニメーションのなめらかさ）は実機で確認をお願いします。

### 追加修正: 展開のたびに座標がズレていく不具合
実機テストで、「畳む→展開」を繰り返すと、展開後のウィンドウ位置が
少しずつ右にズレていき、最終的にウィンドウの一部が画面外に出てしまう
不具合が報告されました。

**原因**: アンカー先の座標（右端に寄せる場合の基準位置など）を、
「ウィンドウ自身が直前に報告した`window.x`/`window.width`」から毎回
計算していました。実機では`resize()`/`move()`で指定した値と、実際に
OSが適用した値の間にわずかな誤差が生じることがあり、この誤差を
毎回のサイクルで積み上げてしまっていました。

**修正**: アンカー先の座標を、ウィンドウの自己申告値ではなく
「ディスプレイの絶対座標（`screen.x` / `screen.x + screen.width` /
`screen.y`）」から計算するように変更しました。`collapse_window()`が
呼ばれた時点でのディスプレイ座標を記録しておき、対応する
`expand_window()`でもその同じ値をそのまま再利用します。これにより、
ウィンドウの自己申告値に多少の誤差があっても、蓄積せずに常に同じ
位置へ戻るようになります。

意図的に「resize/moveのたびに1pxずれて自己申告する」モックウィンドウを
使って5回連続で畳む→展開を繰り返すテストを行い、右端の位置が
（誤差込みでも）1920px付近に留まり続け、ズレが蓄積しないことを
確認しました。

### 追加修正: 「自動的に隠す」で左端の場合だけ畳みきれない不具合
実機テストで、右端では正しく細いバー状に畳まれるのに、**左端では
畳んでも幅が136px程度までしか縮まらず、見た目上「畳みきれていない」**
という不具合が報告されました。

**原因**: 実測ログにより、Windowsのネイティブウィンドウ枠は136px未満
には縮められないというOS側の制約があることが判明しました。この制約
自体は左右どちらでも同じですが、右端側は`x = 画面右端 - 狙った幅`と
いう計算式のおかげで、縮めきれない分がたまたま画面の外（右方向）に
はみ出して「偶然隠れて」見えていただけでした。左端側は`x`を画面左端に
固定する式だったため、縮めきれない分がそのまま画面内に見えてしまって
いました。

**修正**: 左端の場合も、実際に適用された幅を都度読み直し、縮めきれない
分を画面外（左方向のマイナス座標）へ意図的にはみ出させることで、右端と
同じ理屈で隠すようにしました。

## ニコニコ動画対応（今回の更新分）

YouTubeと同様に、ニコニコ動画についても検索・マイリスト・再生・
コメント表示に対応しました。実機での試行錯誤が多かった機能のため、
経緯を詳しく残します。

### 検索・並び替え
公式のスナップショット検索API v2を使用。`_sort`パラメータで並び替え
（再生数順・投稿日時順・コメント数順など）にも対応しました。YouTube
側も`order`パラメータで同様に対応しています（関連度順・日時順など）。
選べる並び替え項目はソースごとに異なるため、UI側でも動的に切り替えて
います。

### マイリスト（公開・非公開の両方に対応）
ニコニコにはYouTubeのOAuthに相当する「自分のマイリスト一覧を自動列挙
する」公式手段が無いため、2つの方式を用意しています。

1. **公開マイリストの手動登録**: マイリストのURL/IDを入力して登録する
   方式。ログイン不要。
2. **ログインして自分のマイリストを自動取得**（非公開のものも含む）:
   後述のログイン機能を使い、以下の非公式APIで取得します。
   - 一覧: `GET https://nvapi.nicovideo.jp/v1/users/me/mylists`
   - 特定のマイリストの中身: `GET https://nvapi.nicovideo.jp/v1/users/me/mylists/{mylist_id}?pageSize=100&page=1`

   いずれも、ユーザー自身がブラウザの開発者ツール（Networkタブ）で
   実際の通信を確認することで特定できたエンドポイントです。仕様書は
   存在しません。当初`/v1/users/{数値ユーザーID}/mylists`という別の
   エンドポイントを使っていましたが、これは「投稿した動画」という
   別物の自動生成リストを返すだけで、正しいものではありませんでした。

   中身取得は、まずログイン中アカウント自身のエンドポイント
   （非公開にも対応）を試し、404等で失敗した場合（他人の公開マイリスト
   をURL登録したケースなど）は、従来の公開マイリスト専用エンドポイント
   （`v2/mylists/{id}`）にフォールバックする実装にしています。

### ニコニコ動画への非公式ログイン
YouTubeのOAuthに相当する公式なログイン手段が無いため、別のpywebview
ウィンドウで通常のニコニコログイン画面を開いてもらい、ログイン完了
（ログイン用ドメインから離脱したことで判定）を検知したら、そのウィンドウ
のCookie（`user_session`）を取り出して使う、という非公式な方式を
取っています。

`user_session`は実質的にパスワードと同等の強さを持つ、アカウントへの
フルアクセス権を持つ値です。**設計方針として、デフォルトではこれを
プロセスのメモリ上にのみ保持し、ディスクには一切保存しません**
（`nico_auth.py`）。アプリを終了すればセッションは失われ、次回起動時は
必ず再ログインが必要になります。

開発中の動作確認を楽にするため、`nico_auth.py`内の
`PERSIST_SESSION_FOR_DEV`という変数を`True`にすると、ログインセッションを
ディスク（`nico_session_dev.json`）に保存し、次回起動時に自動的に
再利用するようになる抜け道も用意しています。**この変数は開発時にだけ
使うもので、一般公開版をビルドする前には必ず`False`に戻す必要が
あります**（コード内に警告コメントを明記済み）。

Cookieの取得（`window.get_cookies()`の戻り値）は、Windows実機で
`http.cookies.SimpleCookie`のリスト（各要素が「クッキー名: Morsel」の
ミニ辞書）という、想定と違う形で返ってくることが実機ログから判明した
ため、複数の形状に対応できる抽出ロジック（`api.py`の
`_extract_cookie_value`）にしています。

### 動画再生（埋め込み） — 最も試行錯誤した部分
現在の実装は、以下のURLを直接`<iframe>`のsrcに設定する方式です。

```
https://embed.nicovideo.jp/watch/{動画ID}?persistence=1&oldScript=1&from=0&allowProgrammaticFullScreen=1&w=720&h=480
```

この形に落ち着くまでの経緯:

1. 素朴に`<iframe src="https://embed.nicovideo.jp/watch/{id}">`を試すも、
   再生開始直後に`unexpected_error`が一貫して発生
2. ニコニコが共有ダイアログで公式配布している埋め込みscriptタグ方式
   （`<script src="https://embed.nicovideo.jp/watch/{id}/script?w=..&h=..">`）
   を試すも、CloudFront側で403エラー
3. ユーザー自身がブラウザの開発者ツールで手動検証し、403の原因が
   「scriptタグが生成するiframeのURLに含まれる`referer=`クエリ
   パラメータの値に`http://`というスキーム部分が含まれていること」だと
   特定。ただしこれを踏まえてクエリパラメータを直接組み立て直しても、
   まだ`unexpected_error`は解消せず
4. 真因は`referer=`クエリパラメータではなく、埋め込みプレーヤー内部の
   スクリプトが独自に参照している**`document.referrer`**（ブラウザが
   自動的に持つ値）だったと判明。`<meta name="referrer">`をページ全体に
   `no-referrer`で設定すると、今度はYouTube側が「Refererが無い」ことを
   理由にエラー153で再生できなくなったため、**ページ全体ではなく
   `#player-frame`に対して、動画ごと（YouTube再生時/ニコニコ再生時）に
   JSから`frame.referrerPolicy`を動的に切り替える**方式に変更し、
   ようやく安定して再生できるようになった
5. `persistence=1&oldScript=1&from=0&allowProgrammaticFullScreen=1`という
   パラメータの組み合わせは、共有ダイアログのscriptタグが生成する
   iframeを外部ブログ記事で調査した結果と、ユーザー自身が実機で確認した
   実際の生成URLの両方から特定できたもの

**画質について**: 埋め込みURLに`w=`/`h=`（表示予定サイズ）パラメータを
渡すと、プレーヤー側の初期画質判定に使われている可能性が実機検証で
示唆されたため、`w=720&h=480`を固定で渡すようにしています。ウィンドウの
リサイズにリアルタイムで追随して画質が変わるかどうかは未検証・不明な
ままです（このURLパラメータはあくまで読み込み時点の値であり、リサイズの
たびに送り直す仕組みは実装していません）。

**私(Claude)自身では実機のWebView2環境を持たないため、上記の原因究明は
すべてユーザー自身の実機での手動検証（開発者ツールでのNetworkタブ確認や、
パラメータを1つずつ変えての比較）によって進みました。**

### コメント表示
埋め込みプレーヤー自体に、再生バー上のアイコンからコメントのON/OFFを
切り替えるUIが標準で含まれているため、アプリ側での追加実装は不要と
判断しました。

### 断念した機能: リストリピート・単一曲リピート
以下の方式をすべて試しましたが、いずれも実用的な形では実現できず、
**この機能は不採用として、今後再提案しない方針にしています**。

- `jsapi=1`によるpostMessageイベント通知（`oldScript`との併用・単体の
  どちらも、コメント取得自体が失敗する）
- プレーヤー自体の「リピート再生」設定（本家視聴ページのプレーヤー
  設定パネルにあるもの。埋め込み版ではこの設定自体が効かない）
- 本家視聴ページ（`www.nicovideo.jp/watch/{id}`）を直接iframe化
  （クリックジャッキング対策で明確にブロックされる）
- 動画の長さ（秒数）を使い、経過後にiframeごと読み込み直す「タイマー
  方式」（ブラウザの自動再生ポリシーにより、読み込み直すたびに
  再生が一時停止状態になってしまい、毎回手動で再生ボタンを押す必要が
  あった。一時停止・シーク操作でズレる弱点もあり不採用）

背景として、ニコニコ動画自体が2024年のサイバー攻撃からの復旧・
サイトリニューアルに伴い、本家視聴ページ向けの直接制御API
（`__videoplayer`）ですら廃止されている（代替なし）ことが分かっており、
外部からの埋め込みプレーヤーに対して同種の制御を行うことは、現時点では
現実的に難しいと判断しています。

## ウィンドウ管理の追加対応（今回の更新分）

### 前回終了時のウィンドウ位置・サイズを記憶
`config.py`に`save_window_state()`/`load_window_state()`を追加し、
ウィンドウが閉じられる直前（`window.events.closing`）に位置・サイズを
`config.json`へ保存、次回起動時（`window.events.shown`）に復元する
ようにしました。保存された座標が、起動時に実際に繋がっている
どのディスプレイの範囲にも収まらない場合（保存後にモニタ構成を
変えた等）は、安全のため既定サイズ（x1・画面端）にフォールバックします。

「自動的に隠す」で畳んだ状態のまま終了した場合は、畳んだ後の細い幅
ではなく、展開時点の幅・位置を保存するようにしています。

### 画面端スナップ・初期サイズ計算でタスクバーを考慮
これまでは常にディスプレイの解像度いっぱい（`screen.height`、
`y = screen.y`）を使っていたため、タスクバーの上にウィンドウが
かぶってしまう可能性がありました。Windows専用のWin32 API
（`EnumDisplayMonitors` + `GetMonitorInfoW`、ctypes経由で直接呼び出し）
を使い、タスクバー等を除いた「作業領域」を取得できる場合はそちらを
基準にするようにしました（`api.py`の`_get_work_area_for_screen`）。
Windows以外の環境や取得に失敗した場合は、これまで通りモニタ全体の
解像度にフォールバックします。**このAPI呼び出し自体は、この開発
環境（Linux）では検証できないため、Windows実機での確認が必要です。**

### タイトルバーを削除し、独自のドラッグ移動に対応
`webview.create_window()`に`frameless=True`を指定し、OSネイティブの
タイトルバー（アイコン・最小化/最大化/閉じるボタン）を取り除きました。
代わりに、`ui/index.html`内に独自のタイトルバー（`#title-bar`）を用意し、
最小化・閉じるボタン（`api.py`の`minimize_window()`/`close_window()`を
呼び出す）を実装しています。

ウィンドウの移動は、pywebview標準の`.pywebview-drag-region`という
CSSクラスを使う仕組みで実現しています。`easy_drag=True`（pywebviewの
既定値）は、frameless時にウィンドウ全体のあらゆる`mousedown`を
ドラッグ起点にしてしまい、検索ボックスやボタン等の通常のUI操作と
衝突することがソースコード調査で判明したため、`easy_drag=False`にした
上で、独自タイトルバーの背景部分と、区切り線（`<hr>`）にだけ
`pywebview-drag-region`クラスを付けています。ボタン類はこのクラスを
持つ要素の**兄弟要素**として配置し、クリックがドラッグ扱いされない
ようにしています（pywebviewの仕組みは、クリックした要素の祖先を
たどってこのクラスに一致するか判定するため、ボタンをドラッグ領域の
内側に置くとボタンクリックまでドラッグと誤認識されてしまう）。

「ウィンドウの任意の場所からドラッグで移動できるようにしてほしい」
という要望に対しては、密に操作要素が並んでいるUIの構造上、完全に
「どこでも」とはできていません。タイトルバーの背景部分と区切り線のみ
ドラッグ可能な範囲としています。

## 既知の制限

- 🔑ボタン（YouTubeを外部ブラウザで開く）は削除済みです（過去の版には
  存在しましたが、紛らわしいため削除しました）。
- リストリピートは現在表示中のページ（最大20件程度）が対象で、
  検索結果全体（最大100件）や複数ページをまたいだ連続再生には対応して
  いません。
- リストリピート・単一曲リピートはYouTubeのみ対応です。ニコニコ動画は
  技術的に実現できないと判断し、対応を断念しています（詳細は上記
  「断念した機能」を参照）。
- ニコニコ動画のマイリスト機能・ログイン機能は、いずれも非公式・
  未文書化のAPIを使用しているため、ニコニコ側の仕様変更で予告なく
  動かなくなる可能性があります。
- ニコニコ動画の埋め込み再生も同様に、非公式に特定したURLパラメータの
  組み合わせに依存しているため、同様のリスクがあります。
- ウィンドウリサイズ時に動画の解像度がリアルタイムで追随するかは
  未検証です（読み込み時点のサイズのみ`w=`/`h=`パラメータとして
  渡しています）。
- Windowsのタスクバーを考慮した作業領域の取得（Win32 API呼び出し）は、
  この開発環境（Linux）では検証できていません。実機での確認が必要です。
- `main.py`内の`DEBUG_MODE`は`False`にしてありますが、埋め込み関連の
  調査が再度必要になった場合は`True`に戻すと開発者ツールが使えます。
